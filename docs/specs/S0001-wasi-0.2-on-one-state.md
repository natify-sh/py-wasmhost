# S0001: WASI 0.2 imports answered from the State of Preview1

Status: draft
Backlog: B-606 (waits for B-603: several memories in the API)

## Goal
A core module fused from a WASI 0.2 component (its imports are flat `wasi:*` names) runs through wasmhost on every backend that takes host functions, its imports answered by fusedwasi's functions of 0.2 over the
`fusedwasi.p2.State` that `Preview1` already holds. It is shown by a fused program of 0.2 that gives the same output as the 0.1 build of it on each such backend, in a CI run.

The sharing of the state between 0.1 and 0.2 is **not** part of this work: fusedwasi already does it (see Context). The work is to offer the 0.2 imports.

## Context
Checked on 2026-11-05 on the installed fusedwasi 0.1.0a1:
* `fusedwasi.p1.State is fusedwasi.p2.State`, and the same for `Guest` and `Exit` (run in the repository). `wasi_p1_core.py` says there is one `State` and one `Guest` for both families: a descriptor of 0.1 is a map to a
  resource of 0.2 plus what 0.1 keeps (rights, position, the name of a preopen), and the functions of `wasi_p1` work through the operations of 0.2. (The docstring of `fusedwasi/p1/__init__.py` says "other classes";
  that is a mistake in fusedwasi's text, not in its code, and is to be fixed there.)
* `fusedwasi.signatures.find_import(module, name)` finds the function for an import of either family: `("wasi_snapshot_preview1", "fd_write")` gives the function of `fusedwasi.p1.wasi_p1`, and
  `("wasi:cli/environment@0.2.0", "get-environment")` gives the function of `wasi:cli/environment@0.2.12` in `fusedwasi.p2.wasi_p2_cli` (`python_module`, `python_name`, `params`, `takes_comp=True`). A package of
  0.2 is matched whatever its patch version is; `@0.3.x` finds nothing.
* `Preview1` already finds the functions of 0.1 this way (`preview1.py`, `find_import`) and keeps one `State` and a `Guest` for each `imports()`.
* Reported by the earlier work (ROADMAP of 2026-10-28, not re-checked): fusedwasi's neutral tests bind the flat imports on wasmtime-py and on pywasm3.
* **A fused module has one memory for each component** (fusedwasi README: "a memory for each component"). `Guest` takes `memories`, a list with one memory for each component (or a function that gives it, so that a memory that
  moves is followed), and `realloc(comp, old_ptr, old_size, align, new_size)`, the `cabi_realloc` of the component; the p2 functions (`takes_comp=True`) get `comp`, the index of the memory in that list, and trap with
  `no memory N` when there is none. So WASI 0.2 **needs multi-memory**: the engine has to take the module, and wasmhost has to give fusedwasi every memory of the instance and every component's `cabi_realloc`.
* **The engines (measured by CI, SUPPORTS.md, run of `fde7d0d`):** a module with two memories runs on `wasmtime`, `node`, `bun`, `wasm3` and `pyodide`, and **not** on `jsc`, `gi-jsc` and `jscontext`. So WASI 0.2 can not run
  on the JavaScriptCore family, that is not in Pythonista, whatever wasmhost does.
* **Fused modules export their memories, by names that change** (S0003, "Context"): `memory`, `memory$1` with `meld` 0.67.0; `memory$0`, `cabi_realloc$1` in wasmext's runs with 0.64 to 0.65. The host of 0.2 therefore takes the names of the memories and of the `cabi_realloc` of each component from the caller (or finds them by a pattern), not from a fixed convention.
* **wasmhost:** `Memory` is reached as an export (`inst.exports.memory`); a module with several memories is accepted by the parser and runs, but the API has no way to reach memory number N, exported or not (B-603).
  The memories of a fused module may not be exported at all; that is to be read from a real fused module.
* Not known, to be read from fusedwasi and from a fused module before approval: whether the memories of a fused module are exported by name (and which names), or only reachable by index inside the module; what an engine
  gives for a memory that is not exported; how the `cabi_realloc` of each component is exported; what a handle (`[method]output-stream.write`) looks like to the engine.

## The contract
*To be written after the questions below are answered.* What is already clear: no new state and no new `supports` string; a module that asks for `wasi:*` imports is answered from the same `State` as one that
asks for `wasi_snapshot_preview1`; a backend that can not take host functions can not run it (as with 0.1); a module of 0.3 (`@0.3.x`) is refused with a `LinkError` that names the import.

## Tests and probes
* a fused program of 0.2 (built once, the bytes kept in `tests/data`), run on each backend of the matrix and compared with the 0.1 build of the same program;
* one `State` used by a module of 0.1 and then by one of 0.2 sees the files the first made (a cheap check that wasmhost keeps the state between them; the sharing itself is fusedwasi's to test);
* SUPPORTS.md: a row for 0.2 in the WASI table, from the CI run.

## Depends on
B-603 (several memories of one instance in the API: access by index, exported or not, and the list for `Guest.memories`). Without it nothing in this spec can run. Its spec is [S0003](S0003-several-memories.md) (draft); it is measured there that exported and imported memories already work on wasmtime, Node, Bun and (exported only) wasm3, so the open point is how the list in module order is made, and whether the memories of a fused module are exported at all.

## Out of scope
The Component Model (a real component with its own types), WASI 0.3, sockets and threads; any change of fusedwasi.

## Open questions
1. How do the memories and the `cabi_realloc` of each component reach the `Guest`: through exports, and under which names? Read a real fused module (made by `meld`) and fusedwasi's tests first.
2. How does a user get a fused module? Only by running `meld`/`wasm-tools` themselves (wasmhost does not do it)?
3. A class for 0.2 beside `Preview1` (the version is in the name, as the README says), or does `Preview1.imports()` answer whichever family the module declares? A module imports one family, not both.
