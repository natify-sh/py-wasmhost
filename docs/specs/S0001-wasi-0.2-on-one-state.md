# S0001: WASI 0.2 imports answered from the State of Preview1

**Two paths (the owner, 2026-11-05).** (1) **One component** (`wasm-tools component unbundle`, or `meld fuse` given one component): the core module has one memory (`memory`), `cabi_realloc` and the export of the command (`wasi:cli/run@0.2.N#run`); it needs no multi-memory, so it can run on every backend that takes host functions, the JavaScriptCore family (Pythonista) included. wasmext already runs such modules (`examples/wasi2_unbundled`, `docs/WASI_COMPONENTS.md`: 453 KB with DWARF, 78 function imports, 3 exports, 1 memory, 1 table); `meld fuse` on one toy component gave one memory too (checked 2026-11-05, `meld` 0.67.0). (2) **Several components fused by `meld`**: a memory for each component, so multi-memory (S0003); not on the JavaScriptCore family. Path 1 comes first.

Status: draft
Backlog: B-606 (two paths: a single component needs no multi-memory; several fused components need S0003, which is approved and built)

## Goal
A core module fused from a WASI 0.2 component (its imports are flat `wasi:*` names) runs through wasmhost on every backend that takes host functions, its imports answered by fusedwasi's functions of 0.2 over the
`fusedwasi.State` that `Preview1` already holds. It is shown by a fused program of 0.2 that gives the same output as the 0.1 build of it on each such backend, in a CI run.

The sharing of the state between 0.1 and 0.2 is **not** part of this work: fusedwasi already does it (see Context). The work is to offer the 0.2 imports.

## Context
Checked on 2026-11-05 on the installed fusedwasi 0.1.0a1:
* `fusedwasi.p1.State is fusedwasi.p2.State`, and the same for `Guest` and `Exit` (run in the repository). `wasi_p1_core.py` says there is one `State` and one `Guest` for both families: a descriptor of 0.1 is a map to a
  resource of 0.2 plus what 0.1 keeps (rights, position, the name of a preopen), and the functions of `wasi_p1` work through the operations of 0.2. (The docstring of `fusedwasi/p1/__init__.py` says "other classes";
  that is a mistake in fusedwasi's text, not in its code, and is to be fixed there.)
* `fusedwasi.signatures.find_import(module, name)` finds the function for an import of either family: `("wasi_snapshot_preview1", "fd_write")` gives the function of `fusedwasi.p1.wasi_p1`, and
  `("wasi:cli/environment@0.2.0", "get-environment")` gives the function of `wasi:cli/environment@0.2.12` in `fusedwasi.p2.wasi_p2_cli` (`python_module`, `python_name`, `params`, `takes_comp=True`). A package of
  0.2 is matched whatever its patch version is; `@0.3.x` finds nothing.
* `Preview1` already finds the functions of 0.1 this way (`preview1.py`, `find_import`) and keeps one `State` and a `Guest` for each `imports()`.
* **Prototype, 2026-11-05** ([docs/experiments/s0001_wasi2](../experiments/s0001_wasi2/README.md); fusedwasi 0.1.0b1; reran by the orchestrator on wasmtime and wasm3): a core module in the shape of an `unbundle` output (hand-written WAT, not a real
  `unbundle`: the 453 KB module of wasmext was not run) runs through wasmhost on **wasmtime, Node, Bun and wasm3**. It prints `hello from wasip2` through `wasi:cli/stdout` and `wasi:io/streams`, reads the environment through
  `get-environment` (which uses `cabi_realloc`), gets random bytes (an `i64` parameter, correct on wasm3 too), and `wasi:cli/exit` raises `fusedwasi.p2.Exit`, which comes out of the exported call unchanged. `jsc`, `gi-jsc` and `jscontext` were not run (not here).
  How it is wired: the import object is `{"wasi:cli/stdout@0.2.6": {"get-stdout": fn}, ...}` with the module names exactly as the module declares them (so it is built from `Module.imports(module)`, the 0.2 names and versions
  are not known up front as those of 0.1 are); `find_import` maps any `@0.2.N` to fusedwasi's `@0.2.12` and finds nothing for `@0.3.x`; each entry masks its arguments (`i32 & 0xFFFFFFFF`, `i64 & 0xFFFF...`), calls
  `fn(guest, comp, *args)` where the row says `takes_comp` and `fn(guest, *args)` otherwise, and returns a value only if the row has results; the `Guest` is made before the instance with `memories=[a function that gives the
  `Memory` of the instance]` and `realloc=` a function that calls the export `cabi_realloc`, so a `bind` after instantiation works as `Preview1.bind` does. The memories and the `cabi_realloc` of each component are reached by
  **export name, given by the caller** (`memory`, `memory$1`; `cabi_realloc`, `cabi_realloc$1`).
* **Sockets work** (2026-11-05, prototype by a subagent, the orchestrator reran `allow`, `default` and `checkdeny` on wasmtime and wasm3): wasmext's `_sock.wasm` (a core module left by `unbundle`: one memory, 74 function imports all under `wasi:*@0.2.12`, all resolved by
  `find_import`; the entry is `wasi:cli/run@0.2.12#run`) connects to a local server on 127.0.0.1, sends `ping`, gets `pong` and returns 0, on **wasmtime, Node, Bun and wasm3** with `State(network=True)`. The policy is fusedwasi's: **deny by default** (`connect: Permission denied`, run result 1, the server sees nothing);
  `socket_addr_check(ip, port, use)` decides each bind or connect (called once as `('127.0.0.1', 47123, 1)`, `use` 1 = TCP connect), and a check that always says no gives the same denial; `allow_ip_name_lookup` follows `network` and was not tested. A blocking socket call holds the whole backend (one call at a time): a second call from another thread waited 1.1 s on wasmtime, wasm3 and Node while the server delayed
  its reply by 1.5 s; it matters only for a long wait (`listen`/`accept`). Not tested: UDP, listen/accept, IPv6, name lookup, `wasi:http`, Bun for the blocking case, Windows, macOS, Pyodide.
* **`comp` is not in the name of an import.** With two memories, `get-environment` called through an import object built with `comp=0` wrote into memory 0 and used `cabi_realloc`; one built with `comp=1` wrote into
  `memory$1` and used `cabi_realloc$1`. A module that imports the same `(module, name)` twice is listed twice by `Module.imports`, but the engine gives **one** callable to both (measured on all four backends). So for several
  components the host needs the component of each import from outside; how a real fused module distinguishes them is not known (not run with a real `meld` output; wasmext's `cx.imports.json` of its complex fused module is where to look).
* **`meld` tells the host which component each import belongs to** (found 2026-11-05). `meld fuse --emit-import-map <PATH>` (from 0.65; `meld fuse --help` in 0.67.0) writes a JSON map, schema `version: 2`: for each function import
  its `index`, `kind`, `module`, `name`, the owning `component`, the `memory` its pointers index and the `realloc` it allocates with (each `{index|func, export}`, so **the export names come from the map, not from a convention**),
  the string `encoding` and, for a resource intrinsic, the `resource` and its `[dtor]` export (`null`: the source `canon lower` has no such option; `{"unknown": reason}`: could not be traced). Run on the toy pair it gave
  `component: 1` for the one import. wasmext keeps the map of its complex fused module (`py-wasmext/docs/experiments/meld_065/cx.imports.v2.json`, meld 0.65.0): 53 function imports, **no `(module, name)` twice**, components 0 and 3
  (27 and 26 imports), memories `memory` (index 0) and `memory$0` (index 1), reallocs `cabi_realloc` and `cabi_realloc$1`, string encodings and resource intrinsics. **The complex module was then built here** (2026-11-05: wasi-sdk 34.0, wit-bindgen 0.63.0, wasm-tools 1.262.0, `meld` 0.67.0; the sources are wasmext's `docs/experiments/jco_zwasm/complex`:
  two components, `wasm-tools compose`, `meld fuse --exports world --emit-import-map`): a core module of 499 978 bytes with **two memories exported as `memory` and `memory$0`**, **`cabi_realloc` and `cabi_realloc$1`**,
  the export `demo:cx/app@0.1.0#run-all` (and its `cabi_post`), and 47 function imports (42 `wasi:*` and the `demo:cx/store` host interface with its resource intrinsics); its map
  ([cx.import-map.v2.json](../experiments/s0001_wasi2/cx.import-map.v2.json)) has no `(module, name)` twice, the owning components are **0 (24 imports) and 2 (23)** (wasmext's older build numbered them 0 and 3), the memories are
  `memory` (index 0) and `memory$0` (index 1) and the reallocs `cabi_realloc` and `cabi_realloc$1`. So the numbers of the components are not dense, and the suffixes of the names are not the same for memory and realloc
  (`$0` and `$1`): **a convention could not be guessed, the map has to be read.** **It was then run through wasmhost** (2026-11-05, a map-driven prototype of about 100 lines, written by a subagent; the orchestrator reran it on wasmtime and wasm3; the file is in the scratchpad and is to be saved in `docs/experiments/s0001_wasi2/` when CI is idle):
  `demo:cx/app@0.1.0#run-all` returned the same string on **wasmtime, Node, Bun and wasm3**, containing the expected `get=apple,3,[red,big]` (the whole text was not compared with a reference: the docstring of wasmext's script gives only that part), and `cabi_post`
  freed it without an error; the host side of `demo:cx/store` was written in Python as wasmext's `run_cx_fused.py` does (counters new 2, rep 3, drop 2 on all four). Facts about the map that the run showed:
  (1) **`comp` is the `memory.index` of the import in the map** (dense: 0 or 1; the position in `Guest.memories`), not the `component` number (0 or 2); the memory of component 0 is `memory$0` at index 1 and its realloc is `cabi_realloc$1`,
  the memory of component 2 is `memory` at index 0. (2) **Only 16 of the 47 imports have a memory** (`takes_comp` imports: the poll, stream and clock ones, 8 for each component); the others (`get-stdout`, resource drops...) have `memory: null` and need no `comp`. (3) **The second component's duplicate imports are renamed with a suffix
  `$N`** (23 of the 47 names, e.g. `get-stdout$2`, `[resource-drop]error$2`, `[resource-rep]counter$0`), which is why `(module, name)` is unique; `fusedwasi.signatures.find_import` does not know the suffix, so it has to be stripped (`name.split('$')[0]`) before the lookup;
  the suffix is **not** the component number (`$2` for component 2, but `$0` for some imports of component 0), so only the map says which component an import is. **Limit of this run: no `wasi:*` function was called** while `run-all` ran (a counter on the wasmtime and wasm3 paths; stdout stayed empty): the 42 `wasi:*` imports were linked and their signatures checked on all four backends, but none was executed, so the routing of `comp` for the WASI calls is read from the map and not yet shown by a run.
  Not known: what the map says when two components import the same `(module, name)` (the real one has none).
* Reported by the earlier work (ROADMAP of 2026-10-28, not re-checked): fusedwasi's neutral tests bind the flat imports on wasmtime-py and on pywasm3.
* **A fused module has one memory for each component** (fusedwasi README: "a memory for each component"). `Guest` takes `memories`, a list with one memory for each component (or a function that gives it, so that a memory that
  moves is followed), and `realloc(comp, old_ptr, old_size, align, new_size)`, the `cabi_realloc` of the component; the p2 functions (`takes_comp=True`) get `comp`, the index of the memory in that list, and trap with
  `no memory N` when there is none. So WASI 0.2 of a **module of several components** needs multi-memory: the engine has to take the module, and wasmhost has to give fusedwasi every memory of the instance and every component's `cabi_realloc`. A module of **one component** has `comp` 0 and a `memories` list of one entry (`memory`); nothing here applies to it.
* **The engines (measured by CI, SUPPORTS.md, run of `fde7d0d`):** a module with two memories runs on `wasmtime`, `node`, `bun`, `wasm3` and `pyodide`, and **not** on `jsc`, `gi-jsc` and `jscontext`. So a WASI 0.2 module **of several components** can not run
  on the JavaScriptCore family, that is not in Pythonista, whatever wasmhost does; a module of one component has one memory and is not affected.
* **Fused modules export their memories, by names that change** (S0003, "Context"): `memory`, `memory$1` with `meld` 0.67.0; `memory$0`, `cabi_realloc$1` in wasmext's runs with 0.64 to 0.65. The host of 0.2 therefore takes the names of the memories and of the `cabi_realloc` of each component from the caller (or finds them by a pattern), not from a fixed convention.
* **wasmhost:** `Memory` is reached as an export (`inst.exports.memory`); a module with several memories is accepted by the parser and runs, but the API has no way to reach memory number N, exported or not (B-603).
  The memories of a fused module may not be exported at all; that is to be read from a real fused module.
* Not known, to be read from fusedwasi and from a fused module before approval: whether the memories of a fused module are exported by name (and which names), or only reachable by index inside the module; what an engine
  gives for a memory that is not exported; how the `cabi_realloc` of each component is exported; what a handle (`[method]output-stream.write`) looks like to the engine.

## The contract
*Proposal from the prototype, for the owner to approve or change.* A **separate class** beside `Preview1` (the version is in its name, as the README says; the name is open question 5), in a sibling module `wasmhost/wasi/preview2.py`
(about 60 to 80 lines; `preview1.py` is not changed): the same options as `Preview1` (`args`, `env`, `preopens`, `stdin`, `stdout`, `stderr`, `readonly`); `imports(module)`, which needs the `Module` to read the declared names and versions
and raises a `LinkError` for a `wasi:` import fusedwasi has no function for (`@0.3.x` among them); `bind(instance, memories=("memory",), reallocs=("cabi_realloc",))`, the export names of each component, given by the caller; options of the policy that go to the `State` (**the default is deny, confirmed by the owner on 2026-11-05**: a module gets no network until the host says so; files are the same, only the `preopens` given): `network=False`, `socket_addr_check=None`, `allow_ip_name_lookup=None`, `http=False`, `http_check=None` (as fusedwasi names them: deny by default); **a `State` can be shared** (the owner, 2026-11-05): `Preview1` and `Preview2` expose a public `state` and accept `state=`, so that `Preview2(state=p1.state)` sees the files, arguments, environment and streams of `Preview1` (the options `args`, `env`, `preopens` are then not given: they are the state's);
`instantiate(module)`, `start(instance)`; `run(module)`, which calls the export that matches `wasi:cli/run@0.2.*#run` and turns `Exit` into the exit code (a result of 0 from `run` is ok). A separate class is cleaner than
letting `Preview1.imports()` answer both families: building the 0.2 object needs the module, and 0.2 needs the memories and `cabi_realloc`, while 0.1 takes only `instance.exports.memory`. What is clear whatever the shape: no new `supports` string; a module that asks for `wasi:*` imports is answered from a `State` of fusedwasi, as one that
asks for `wasi_snapshot_preview1` is; a backend that can not take host functions can not run it (as with 0.1); a module of 0.3 (`@0.3.x`) is refused with a `LinkError` that names the import.

**The command line (the owner, 2026-11-05):** `wasmhost run` gets a flag **`--allow-net`**, which gives the module of WASI 0.2 `network=True`; without it the network is denied. (`wasmhost run` has to tell a module of 0.2 from one of 0.1 by the names of its imports, `wasi:*` against `wasi_snapshot_preview1`, and use `Preview2` for the first; the finer policy `socket_addr_check` is the library's, not a flag.)

## Tests and probes
* a fused program of 0.2 (built once, the bytes kept in `tests/data`), run on each backend of the matrix and compared with the 0.1 build of the same program;
* one `State` used by a module of 0.1 and then by one of 0.2 sees the files the first made (a cheap check that wasmhost keeps the state between them; the sharing itself is fusedwasi's to test);
* a TCP connect to a local server (as the prototype does) with `network=True`, and the default denial; a `socket_addr_check` that allows one port and denies another;
* a test that `Preview2(state=p1.state)` and `Preview1` see the same file;
* SUPPORTS.md: a row for 0.2 and a row for sockets in the WASI table, from the CI run.

## Depends on
Path 1 (one component): nothing beyond fusedwasi. Path 2 (several components): [S0003](S0003-several-memories.md) (approved, tests built) and the naming of the memories (open question 1). Its spec is [S0003](S0003-several-memories.md) (draft); it is measured there that exported and imported memories already work on wasmtime, Node, Bun and (exported only) wasm3, so the open point is how the list in module order is made, and whether the memories of a fused module are exported at all.

## Out of scope
The Component Model (a real component with its own types), WASI 0.3, `wasi-threads` (threads inside the module: not in WASI 0.2 and not in fusedwasi), and any change of fusedwasi. Sockets and `wasi:http` are not left out: they come through the same `find_import`, denied by default and opened by the options above; the first step is tested for a TCP connect only.

## Open questions
1. *Answered by the prototype (one component):* through exports, by names the caller gives (`memory`, `cabi_realloc` by default). Still open for several components: which names a real fused module has (they vary with the `meld` version, S0003) and how a call tells which component made it (open question 4).
4. **Several components (path 2): where does `comp` come from?** *Answered, 2026-11-05:* not from the name of the import (measured), but from `meld`'s import map (`--emit-import-map`, schema 2: the owning `component`, the `memory` and the `realloc` of each import). The proposal for path 2: `Preview2` takes the map (a path or the loaded dictionary) and makes one entry of the import object for each import with its `comp`, memory and realloc names from the map; no naming convention. Refined by the run: `comp` is the `memory.index` of the import; the name is stripped of its `$N` before `find_import`; the imports that are not `wasi:*` (here `demo:cx/store`) are the user's, passed as an extra import dictionary that the host merges in, and they need the instance (a late-bound reference, as `bind` has) because a resource drop calls the export `...#[dtor]counter`. A generic helper for resource intrinsics (the map has `operation` and `dtor_export`) is possible and is not proposed yet. Still to decide: whether a fused module without a map is refused or taken as one component (the map of the real module has no `(module, name)` twice, since the second component's names carry the suffix).
5. The name of the class and the module (`Preview2`, `wasmhost.wasi.preview2`?). *Sharing a `State` was decided by the owner on 2026-11-05: yes, they share (see the contract).*
2. How does a user get a fused module? Only by running `meld`/`wasm-tools` themselves (wasmhost does not do it)?
3. *Answered, as a proposal:* a separate class (see the contract).
