# S0001: WASI 0.2 (fused modules) over the one fusedwasi state

Status: draft
Backlog: B-606

## Goal
A module of WASI 0.2 that has been fused to one core module (`meld fuse`, or `wasm-tools component unbundle`), whose imports are flat `wasi:*` names, runs through wasmhost over the **same** `fusedwasi.p2.State` that
`Preview1` already uses, so that the files, arguments, environment, clocks and streams of a program are the same whichever version of WASI it asks for. It is shown by a program of 0.2 that runs on every backend that
takes host functions, with the same output as the 0.1 build of it.

## Context
* `wasmhost.wasi.preview1.Preview1` is a host over fusedwasi 0.1.0a1 (pure Python): one `fusedwasi.p2.State` is the world and a `Guest` is each `imports()` (README, "WASI"; BACKLOG B-501).
* The owner decided on 2026-11-04: WASI is fusedwasi 0.1 and 0.2 over one state; the Component Model host is not planned (ROADMAP).
* Reported by the earlier work (ROADMAP of 2026-10-28, not re-checked here): fusedwasi knows the flat `wasi:*` imports of a fused module, and its neutral tests bind them on wasmtime-py and on pywasm3.
* Not known and to be read from fusedwasi before this spec is approved: the exact names and signatures it offers for the flat imports, and whether the `Guest` of 0.1 and the binding of 0.2 can share one `State`.

## The contract
*To be written after the questions below are answered.* The sketch: a class beside `Preview1` (the name carries the version, as the README says: `Wasip2`-like, not `Preview1`) with the same options (`args`, `env`, `preopens`,
`stdin`, `stdout`, `stderr`, `readonly`), `imports()`, `bind(instance)`, `instantiate`, `start`, `run`; and a way to give both over one world. `supports(...)` needs no new string: a backend that can not take host functions
can not run it, as with 0.1.

## Tests and probes
* a fused program of 0.2 (built once, the bytes kept in `tests/data`), run on each backend of the matrix, and compared with the 0.1 build;
* a test that 0.1 and 0.2 over one `State` see the same files and arguments;
* SUPPORTS.md: a row per WASI version in the WASI table, from the CI run.

## Out of scope
The Component Model (a real component with its own types), WASI 0.3, sockets and threads.

## Open questions
1. What exactly does fusedwasi offer for 0.2 today (names, signatures, the shape of the `State` it shares)? Read its source and tests first.
2. How does a user get a fused module? Only by running `meld`/`wasm-tools` themselves (not planned for wasmhost to do it)?
3. One class for both versions, or one for each over a shared `State`?
