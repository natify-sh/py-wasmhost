# S0004: WASI 0.2 of several components, through meld's import map

Status: approved by the owner on 2026-11-05 (the answers to questions 1, 2 and 4 below as proposed, with the correction to question 2)
Backlog: B-606 (path 2 of S0001)

## Goal
A core module that `meld` fused from **several** WASI 0.2 components runs through `Preview2` on every backend that takes multi-memory and host functions, each `wasi:*` import of each component reaching **its own** memory and
`cabi_realloc`, the routing taken from the import map that `meld fuse --emit-import-map` writes. It is shown by a module of two components in which each component calls WASI (a write to stdout from each, through its own memory) running on those backends, in a CI run.

## Context
* [S0001](S0001-wasi-0.2-on-one-state.md) (approved, step A built): `Preview2` for **one** component; its `bind` refuses anything but one memory and one `cabi_realloc`. [S0003](S0003-several-memories.md) (built): several memories of a module are several `Memory` objects.
* A module fused from several components has a memory for each (meld's default strategy, `--memory auto`, always resolves to `multi`), and fusedwasi's `Guest` takes a list `memories` and a `realloc(comp, ...)`, with `comp` the index into that list for the functions that `takes_comp`.
* **`comp` is not in the name of an import**, and the numbers and names are not guessable (measured 2026-11-05 on the complex module built here, meld 0.67.0, `--exports world`): memories `memory` (index 0) and `memory$0` (index 1), reallocs `cabi_realloc` and `cabi_realloc$1`, the owning components numbered 0 and 2. `meld fuse --emit-import-map PATH` (from 0.65) writes the answer, schema `version: 2`:
  for each function import `index`, `kind`, `module`, `name` (the second component's duplicates carry a `$N` suffix, so `(module, name)` is unique; `find_import` does not know the suffix), the owning `component`, the `memory` its pointers index and the `realloc` it allocates with (`{index|func, export}`), the string `encoding`, and for a resource intrinsic a `resource` object; `null` means the source `canon lower` has no such option, `{"unknown": reason}` that it could not be traced. A copy of the map of the complex module is in `docs/experiments/s0001_wasi2/cx.import-map.v2.json`.
* A prototype by a subagent (`cx_host.py`, in the scratchpad of the session, not in the repository) ran `demo:cx/app@0.1.0#run-all` of that module through wasmhost on wasmtime, Node, Bun and wasm3 with the string result as expected, using `comp = memory.index` and stripping the `$N` suffix. **No `wasi:*` function was called during that run**, so the routing of `comp` for WASI calls is read from the map and not yet shown by a run: this spec has to show it.
* **Measured 2026-11-05 (meld 0.67.0, two small components A and B built here with wit-bindgen and wasi-sdk 34, each calling `get-arguments` and writing its own text to stdout; the work is in the scratchpad of the session, the sources go to `docs/experiments/s0004_meld/`):**
  `--memory multi`: 2 memories (`memory`, `memory$0`), 2 reallocs (`cabi_realloc`, `cabi_realloc$1`), 6 wasi imports (the second component's with `$2`), a complete map; routing by `comp = memory.index` prints the right text on wasmtime, Node, Bun and wasm3, and **a host that gives every import one comp prints corrupt output** (NUL bytes, the other component's text).
  `--memory shared --address-rebase` (also `--pack-rebase`): **1 memory, 1 exported `cabi_realloc`, 3 wasi imports with no suffix**: meld merges the imports of the two components into one each, and the map says so (`also_components: [2]`, `realloc: {"unknown": "canon lowers of one fused import disagree..."}` for `get-arguments`). Seen from the host this is **the shape of one component** and the host has no way to tell the callers apart. It ran correctly on the four backends, but only with an allocator whose `free` is a no-op: with a stand-in that traps on a free of another component's block it trapped; a real allocator in this mode was **not** run, because meld refuses `memory.grow` under address rebasing (so a component built with wasi-libc's malloc, as CPython is, can not be fused this way at all) and refuses `--memory shared` without rebasing (overlapping data segments). Only two components were tried.
* The engines: a module with two memories is refused by JavaScriptCore (`jsc`, `gi-jsc`, `jscontext`) and accepted by wasmtime, Node, Bun, wasm3 and Pyodide (SUPPORTS.md). `meld --memory shared --address-rebase` gives one memory but meld calls it unsound if any component grows memory; it is not proposed here.
* The imports of a fused module that are not `wasi:*` (here `demo:cx/store` and its resource intrinsics) are the user's; the prototype wrote them in Python (counters new, rep, drop; a resource drop calls the export `...#[dtor]counter`).

## The contract
*Proposal, for the owner to approve or change.*
* `Preview2` takes `import_map=` (a path, or the loaded JSON as a dictionary). With it: `imports(module)` makes one entry for each `wasi:*` import of the module, found in the map by `(module, name)`, with the `comp` of that import (its `memory.index`, `0` when `memory` is `null`), the name stripped of its `$N` before `find_import`; `bind(instance)` takes the export names of the memories and of the reallocs from the map (the arguments `memories=` and `reallocs=` are for a module without a map), and builds `Guest.memories` and `realloc` for all components.
* **When a map is needed (the rule, from the measurement above):** the number of exports whose name starts with `cabi_realloc` (`cabi_realloc`, `cabi_realloc$1`, ...). **One:** the module is run as one component, as in S0001, with no map; this includes a `--memory shared` fusion (one memory, one realloc), for which the documentation says that every call is served by the one realloc, that it is safe only with an allocator that does not free another component's blocks, and that meld itself calls the mode unsound. **More than one and no map:** `ValueError` with the hint: give `import_map=`, made by `meld fuse --emit-import-map`, or fuse one component. (The count of memories is not the rule: a shared fusion has one memory and several components.)
* Errors, each naming what is wrong: a map whose `version` is not 2 (`ValueError`); a `wasi:*` import of the module that is not in the map, or whose entry says `{"unknown": ...}` (`LinkError`); a module with several `cabi_realloc*` exports and no map (`ValueError`, as above); a module that lists the same `(module, name)` twice (it can not be routed: `LinkError`).
* `Preview2` answers only the `wasi:*` imports; the others (resource intrinsics, user interfaces) are given by the caller in the import object it merges (`{**wasi.imports(module), **mine}`), and may need the instance (late binding, as `bind` has). A helper for the resource intrinsics is not part of this spec.
* `wasmhost run` gets `--import-map PATH` for the same (the command line of S0001 step B first).
* No new `supports` string: a backend without multi-memory refuses the module itself (SUPPORTS.md says which).

## Tests and probes
* the map: a valid one (the copy of the complex module's, 47 imports), version 3, an `{"unknown": ...}` entry, an import missing from the map, a module with several memories and no map, a module with a duplicate `(module, name)`: errors and messages (no binary needed);
* **routing**: two small components built from WAT, each calling `wasi:cli/stdout` and `wasi:io/streams` `blocking-write-and-flush` with the **memory and `cabi_realloc` of its own** (the `canon lower` options), fused with `meld fuse --emit-import-map`; the bytes of the fused module and its map are kept in `tests/data/wasi2/` with the commands that made them; the test shows that each component's text arrives in the right order and that each call read its own memory (the second component's text sits at an address that is wrong in memory 0), on every backend of the matrix;
* the complex module (500 KB, `docs/experiments`) stays an experiment, not a test: it needs the host side of `demo:cx/store`;
* a row for WASI 0.2 of several components in the WASI table of SUPPORTS.md, from the CI run (a probe module of the routing test); the self-test step asks `supports("imports")` and the engine, and says "not available" where the module is refused.

## Out of scope
Building the map or the fused module (meld does it); a generic helper for resource intrinsics; special handling of a `--memory shared` fusion (it runs as one component, with the caution in the contract); JavaScriptCore for several memories (a shared fusion has one memory and was not tried there); WASI 0.3; `wasi-threads`; any change of fusedwasi or meld.

## Open questions
1. *Answered 2026-11-05 (the owner, "ok"):* `import_map=` takes a path or the loaded dictionary; `wasmhost run --import-map PATH`.
2. *Answered 2026-11-05 (the owner, then measured):* a module that looks like one component (one memory, one `cabi_realloc`) runs as the one-component case of S0001 and needs no map; a module with several `cabi_realloc*` exports and no map is refused. The first draft followed the number of memories; the measurement showed that a `--memory shared` fusion of several components has one memory and one realloc, so the rule follows the reallocs (see the contract).
3. Does a real map ever list the same `(module, name)` twice (the one measured does not), and what is `comp` then?
4. *Answered 2026-11-05 (the owner, "ok"):* schema 2 (read from `meld` 0.65 and 0.67); a map of another version is refused with a message; the documentation says it.
5. *Answered 2026-11-05 (the owner, "ok"):* built once by a developer; the bytes of the fused module and its map are kept in `tests/data/wasi2/` with the commands that made them.
